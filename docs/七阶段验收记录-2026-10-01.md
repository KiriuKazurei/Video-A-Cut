## 2. 已复现问题及修复方案

### F7-01 / P1：旧执行可修改同 Agent 重领后的新任务

位置：`control-plane/internal/mcpserver/tasks.go` 的 `progressArgs`、`heartbeatArgs`、`failArgs`；`internal/service/agent.go:48`；`internal/service/task.go:259`、`:366`、`:427`；Python `ingest/loop.py` 的租约与失败上报、`ingest/common.py` 的进度上报。

原因：每次领取确实刷新 `execution_id`，checkpoint 与结果登记也验证它，但 heartbeat/progress/fail 请求只带 `task_id`。控制面只检查 Agent 身份、当前任务和租约，不能辨别同一 Agent 的旧执行。

复现：领取一个真实 service 导入任务，模拟回收为 queued，再由同一 Agent 重领，断言执行 ID 已改变。用旧进程持有的 `task_id` 分别调用 heartbeat、progress、fail。三项都错误地返回成功：新任务被续租、进度变为 0.9，或变为 failed。新增独立诊断三个子用例均 FAIL，而原有测试只覆盖旧结果与旧 checkpoint 的拒绝。

影响：旧执行的迟到失败可终止正在运行的新执行；旧进度污染当前状态，旧心跳可错误延长租约。长任务恢复不能视为验收完成。

方案：给通用 MCP 写请求增加兼容旧任务的可选 `execution_id`，但对有 ingest binding 的任务必须提供当前值。所有导入任务写入在同一事务中验证 execution、持有者、状态、租约及治理；普通历史任务保持兼容。Worker 每次领取输入后固定当前执行 ID，租约线程、进度和失败上报使用该值；不能每次重新取最新 ID 来让旧执行冒充新执行。

复验：旧执行 heartbeat/progress/fail/checkpoint/submit 均被拒且不改变新任务；当前执行正常；不同 Agent、取消、锁定/隐藏和普通旧任务兼容回归通过。

### F7-02 / P1：MCP 网络中断可退出整个 ingester

位置：`workers/python/vac_worker/ingest/loop.py:72`、`:150`；`ingest/common.py:324`、`:359`、`:373`；`scripts/Start-LocalPipeline.ps1` 的进程存活检查。

原因：`process_ingest` 未处理 `TransportError`，外层循环调用它也没有异常隔离。取输入、登记 checkpoint 或结果提交重试耗尽时，连接错误向顶层传播。提交虽重试 4 次，耗尽后仍抛出；`recover()` 再登记 receipt 的连接失败也会传播。

复现：用无网络、无媒体的故障注入客户端在 `get_task_input` 返回 TransportError，异常直接逃出 `run_ingest_loop`；另在已发布 receipt 的恢复提交边界注入同类异常，逃出 `process_ingest`。诊断脚本输出两条 CONFIRMED。

影响：服务短暂不可达会让 ingester 退出；使用启动脚本时，脚本发现自有 Worker 退出，会停止这一会话的其余控制面和 Worker。当前还不能保证发布后断线的恢复闭环。

方案：把传输失败作为连接/恢复状态处理，不伪报永久媒体失败。当前执行在有界退避和取消检查下恢复取输入、checkpoint/receipt 登记；确认失去租约时停止该执行，保留可验证成果。单任务传输异常不能逃出 Worker 主循环。重启/重领需要在当前执行身份下验证并复用旧的已完成成果，不直接放行旧 execution 的迟到提交。

复验：在取输入、checkpoint、发布后提交及 receipt 恢复处分别断开/恢复控制面，验证 Worker 不退出、不发生重复登记、不重复全部扫描/编码；超过重试预算后仍能继续轮询并让队列合法恢复。用真实启动脚本确认单次连接故障不会关闭整个会话。
