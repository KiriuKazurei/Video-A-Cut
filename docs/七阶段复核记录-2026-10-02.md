## 2. 必须修复的问题

### F7-R01 / P1：新实例会将另一有效实例的进程当作遗留进程结束

位置：`workers/python/vac_worker/ingest/supervise.py:142`、`:150`、`:206`、`:231`；`ingest/loop.py:347`；`scripts/Start-LocalPipeline.ps1:50`。

所有实例共用 `.vac-runtime/owned.json`。新实例加载其中其他 runtime 的 PID 后，`recover_orphans()` 仅确认记录中有 marker/runtime 字符串以及 PID 仍存活，就把它们加入自身停止列表。它没有验证旧 Worker 是否死亡、进程创建时间、实际进程身份或服务端是否批准替换；恢复发生在 claim 的实例冲突检查之前。启动脚本兜底停止也直接使用该文件里的 PID。

独立探针让旧实例登记一个模拟存活媒体 PID，再启动不同 runtime；新实例发起对该 PID 的结束调用。**这里只拦截并记录信号，没有实际结束外部进程。** 可见新实例即使最终被服务器拒绝领取，也可能已干扰有效旧执行；PID 复用还可能造成误杀。

解决：实例独立且互斥写入进程注册表；记录并核验父实例、创建时间和进程身份。区分活跃旧实例与确已崩溃的 owner，服务端 replace/reject 决策必须先于回收。未知或身份不匹配的进程保持隔离并报告清理受阻。Worker 和启动脚本使用同一套核验规则。

验收：同时启动两个真实实例，reject 不影响旧媒体树；合法 replace 按控制命令排空；崩溃后的 owned 子孙可回收；模拟 PID 复用和无关进程均不得被结束。

### F7-R02 / P1：物理锁不可恢复，且没有绑定实际共享资源

位置：`ingest/supervise.py:272`、`:280`；`ingest/loop.py:250`；`control-plane/internal/service/ingest_worker.go:177`。

`PhysicalLock` 依赖 `O_CREAT|O_EXCL` 创建文件，并未持有操作系统资源锁。正常释放会删除文件，Worker 崩溃则永久留下文件。恢复删除要求旧 PID 已被 registry 登记且 marker 等于新 registry 的 marker；锁登记的是 Worker 父 PID，registry 主要登记媒体子 PID，新实例的 marker 又重新生成，普通重启无法满足条件。现有真实跨进程测试在杀死 holder 后明确断言 `blocked`，没有证明重启后能够恢复。

此外，Go `IngestInput` 没有 `resource_keys/resource_key`，Worker 因而总是回退到 `task-{task_id}`。新 task 的物理锁与旧 task 不相同，不能保护共同的源快照等实际资源；服务端逻辑屏障不能代替要求中的跨进程物理保护。

解决：服务端返回稳定、受控的实际资源键，Worker 对同一资源使用相同锁身份。用 Windows 系统锁或命名互斥机制持有权威锁，结合 R01 的进程身份核验处理崩溃后的 owner；保留审计元数据，不能因文件存在永久阻塞，也不能因租约过期直接删除未知锁。

验收：有效旧 owner 禁止新写入；父进程崩溃和子孙排空后新 runtime 可恢复；不同 task 对同一 source 无并发写；未知 owner 仍安全阻断。

### F7-R03 / P1：租约过期后停止确认被本地重试预算阻止

位置：`ingest/loop.py:182`、`:190`、`:293`；`ingest/supervise.py` 的 `LocalLease.retry_until`。

`_ack_stopped()` 虽创建新的 Halt，但仍将旧 LocalLease 传入 retry。租约到期或距到期不足停止余量时，retry 在第一次 HTTP 调用前即报预算耗尽。独立探针确认 ACK 调用列表为空。另一条租约截止分支直接返回 `suspended_connection`，没有持久待发送 ACK。服务端回收租约会建立 draining 屏障，旧 owner 的确认没有到达时，新执行无法 begin。

解决：停止确认使用独立、有界、不依赖业务租约的重试预算，持久化停止结果并在重连后补发；始终保留旧执行身份。必须先验证 owned 树退出、实际锁释放和必要清理完成，再确认 stopped；清理失败发送 cleanup_blocked。崩溃重启也需要有受控的旧 owner 排空确认途径，不能靠 TTL 放行。

验收：断网跨越租约、控制面回收后恢复连接，旧 ACK 最终可达且幂等，新执行解除对应屏障；ACK 不修改新任务进度。

### F7-R04 / P1：跨执行 sealed 成果接管没有实现

位置：`ingest/common.py:541`、`:572`；`control-plane/internal/service/execution_flow.go:570`、`:581`。

服务端候选只有旧 execution、generation、stage、input 哈希和 checkpoint 数量；Worker 的 `note_recovery_candidates()` 只把旧 ID 写入 journal。`recover()` 随后仅检查**当前执行目录**的 receipt，没有获取、校验或接管旧 sealed 包，也没有消费旧执行未登记单元的本地 journal。

独立探针提供相同 stage/input 的候选和旧 receipt、切换到新 scope，结果 `recovered=false`、无新 package、无恢复登记调用。探针只证明候选分支没有接管动作；不是对旧完整媒体包合法性的验收。代码路径也没有后续的 sealed 包接管实现。

解决：Go 返回经过授权的旧成果引用及完整核验信息，不能由 Worker 随意扫描历史目录。排空后核验输入、策略、源版本、分析/选择修订、媒体和 worker 兼容性及文件哈希，接管已验证成果；新执行生成自己的 receipt 与登记请求，旧 receipt/历史包保持不变。未登记的完整块和扫描结果需要受控 journal 发现、验证和补报，不只恢复服务端已有 checkpoint。

验收：复制、扫描、转码及发布后分别杀 Worker/回收重领，统计复用字节、完成单元和 FFmpeg 调用；仅重做不完整尾部。旧成果篡改或指纹变化必须拒绝。

### F7-R05 / P1：已成功提交的结果状态查询返回 stale_execution

位置：`control-plane/internal/service/execution_guard.go:240`、`:247`；`internal/service/execution_flow.go:533`。

`permitOperation` 的结果查询仅放行 current/revoked，成功执行为 succeeded，既不是 current 也不是 revoked。查询回调里虽然有 committed 分支，却被切面提前拦截。

独立 service 探针创建并实际登记合法 probe 包，任务确认 succeeded，同请求 submit 重放也成功；随后相同原 owner 查询该请求，返回 stale execution，断言失败。这会破坏“事务提交但应答丢失”的查询闭环。现有 lost-submit 测试用 mock 返回 committed，未覆盖真实 service 状态转换。

解决：为结果查询增加严格限于原 owner、原 runtime/execution/generation 和对应 request_id 的成功历史只读例外，不能放宽 heartbeat/progress/checkpoint/submit 的旧写入权限。补真实事务提交后丢应答的 HTTP/MCP 测试，并验证无重复状态推进或审计。

验收：成功提交后、控制面重启后以及任务后续执行推进后，原请求均可查询 committed；其他实例/请求不得读取或借此写入。

### F7-R06 / P1：启动阶段断线仍会使 Worker 退出

位置：`ingest/loop.py:350`；`vac_worker/__main__.py` 的顶层异常处理；启动脚本的重启判定。

首次 `client.list_tools()` 在主循环异常隔离之外。独立注入启动连接错误，`TransientTransportError` 直接逃出 run_ingest_loop，顶层返回退出码 2。脚本可以局部重启，但持续断线会很快耗尽 60 秒内三次重启额度，连接恢复后仍无法自行恢复角色。因此不能将“任务内故障已隔离”写成“一整套连接恢复已完成”。

解决：协议发现和初次注册加入可取消、有界退避的连接监督；短暂传输问题保持该角色待连接，鉴权或协议错误进入明确 degraded 状态。启动脚本永久错误判断应覆盖日志实际输出位置：Python fatal 输出到 stdout，目前脚本只读取 stderr，需避免永久错误被误当短暂错误重复重启。

验收：先启动 Worker、延迟启动/恢复控制面，Worker 不退出并最终正常注册领取；401/403/不兼容协议不高速重试，其他服务保持运行。

### F7-R07 / P2：前后端执行状态协议不一致，真实运行状态显示错误

位置：`control-plane/internal/service/ingest_view.go:34`；`webui/src/ingest.ts:92`、`:119`、`:135`；`IngestPanel.tsx:136`。

Go 输出 `status/checkpoints_done/recovery_from` 和 `connection=suspended`；前端读取 `state/completed_units/recovered_from_execution_id/begun` 和 `connection=interrupted`。API 层没有转换。

独立探针将真实 service 的 running JSON 输入前端函数：`progress=null`、`notStarted=true`；同后端形状的 waiting_resource/suspended 不显示对应提示。构建能通过，因为 TypeScript 的 request 泛型不验证运行时 JSON，现有四项 UI 测试也没有覆盖导入状态。

解决：统一并版本化 Go JSON 与 TypeScript 契约，正确映射开始、等待、断线、恢复、清理、完成状态；区分服务端已确认 checkpoint 和本地保留单元，不能编造恢复数量。增加真实 API 响应驱动的组件测试，再检查动态表单与各窗口宽度。

验收：running 显示真实进度；allocated/waiting 不显示已开始；断线/恢复/清理状态与控制面一致；ready 不再显示尚未开始。
