## 3. 持久化契约

### 修订 Revision

字段至少包含 revision_id、asset_id、parent_revision_id、schema_version、package_ref、edl_sha256、evidence_manifest_sha256（无证据时明确空）、created_at、created_by、reason。包引用必须是 delivery_root 内已验证的相对路径。资产内容修订保存为不可变包，批准/撤销记录在数据库，不通过修改原包写回。

人修改场景或草稿会产生新修订，原修订与旧导出保留。修改后的包复制所需媒体与证据并重新校验；保存后的 EDL 与修订哈希必须一致。不得允许 UI 上传任意 EDL 或填写主机绝对路径。旧资产首次进入流程时显式建立初始修订，不伪造历史修订。

场景必须有稳定 scene_id，草稿必须有稳定 narration_id；sort 改变顺序后 ID 不变。旧 EDL 没有 ID 时由首次修订一次性分配，后续不按数组下标重建 ID。沿用既有字段，同时增加修订关联，Worker 和导出器不得丢弃未知扩展字段。

### 流程 WorkflowRun

字段至少包含 run_id、asset_id、base_revision_id、current_revision_id、status、stage、version、created_at、updated_at、error_code、blocked_reason。阶段映射单独持久化 task_id、stage、input_revision_id、output_revision_id、attempt_of；重试创建新 task_id，不清空旧任务与审计。

流程状态使用 created/running/awaiting_review/failed/cancelled/ready_for_acceptance。人工结论存独立 AcceptanceRecord；任务 succeeded 或 ZIP 可下载均不能表示人工验收通过。现有 Task 状态机保持其含义，不把 awaiting_review 塞入任务状态；现有 Asset.human_approved 也不能替代某一草稿或最终包的批准。

每资产最多一个活动流程，由数据库事务及唯一约束保证，不能只靠前端禁用按钮。当前流程进入 ready_for_acceptance 后可基于明确修订启动新流程，但旧包及验收记录不可覆盖。

### 审查与验收

场景审查保存 revision_id、scene_id、decision（confirmed/rejected）、备注、actor、时间；确认须关联实际证据哈希。解说批准绑定 asset/run/revision/narration_id 和服务计算的草稿哈希，不接受客户端直接指定批准哈希。哈希规则继续复用四阶段文本/起止/来源规范，并通过修订 ID 绑定模型与证据版本；Go/Python 用共享 fixture 校验一致性。

AcceptanceRecord 绑定 run_id、export_revision_id、最终 manifest 哈希、检查项目、结果、记录人、时间、说明。检查项目包括内容忠实度、证据追溯、浏览器操作、Premiere 导入、切点/帧率、字幕/音频/ducking。结果只有 pending/passed/failed，默认 pending。人工记录不能由 Worker 或模型创建。

## 4. 流程与复核门禁

1. 人选择一个资产修订启动流程。先验证素材、角色与 Worker 配置是否满足运行条件；缺模型时给出明确配置错误，不能退回 builtin 并宣称真实识别成功。
2. recognize 成功后进入**场景审查**，展示 JPEG、源取样时刻、标签、置信度、rank 与模型来源。人可修改 label/rank，确认有证据的场景。全部场景确认后才生成 sort → narrate 任务。
3. narrate 成功后进入**草稿审查**。人查看来源场景、文本和时间窗，可修改草稿，批准或撤销。全部需要的草稿获当前版本批准后才生成 tts → subtitle → mix → export。
4. export 提交成功且交付清单校验通过，流程为 ready_for_acceptance。显示 ZIP 与待人工验收项目，不自动记录 passed。

本阶段 WebUI 流程默认强制以上人工门禁。四阶段操作员自动策略仍可保留为单独的显式配置能力，但流程不能被 Worker 的自动策略越过：控制面未放行便不创建下游任务。自动测试可由测试用人工 REST 客户端批准合成 fixture，记录为工程测试而非用户实际验收。

恢复时由控制面重建持久化状态并核对已完成任务，补建遗漏的下一阶段任务；不能依赖进程内计时器唯一推进。阶段完成事件与创建下一阶段须通过事务或可幂等恢复的推进记录连接。服务重启、重复 submit_delivery、SSE 重连均不得重复建任务。

所有任务绑定输入修订：首阶段绑定选定包；依赖阶段只绑定其上游成功产物，不绑定将来可能变动的 asset.artifacts。MCP 增加受限 `get_task_input(task_id)`，返回已验证的输入 EDL、包引用、修订及适用批准；按角色、任务归属、有效租约和资产可见性检查，响应不含凭证。Python 与 Node 都消费同一契约。原任务入口保留兼容路径，并明确区分是否属于版本化流程。

提交时核对 run、task、input_revision、lease 与活动流程版本。过期任务、被撤销流程和旧修订产物不得更新当前资产或流程；即便磁盘已有包也必须拒绝注册并记录原因。数据库提交失败的孤立包使用可重试登记/显式回收记录，不删除已登记历史包。文件暂存与 SQLite 不能假装组成一个事务：采用写暂存、校验、原子改名、事务登记及恢复扫描，并覆盖各故障点。

## 5. 人工编辑与重跑规则

本阶段编辑只支持场景 label/rank 和解说 text/start/end/source_scene_id。不支持任意视频切点、增删轨道、素材路径或渲染参数编辑。来源场景必须属于当前修订，解说窗口必须在对应视频范围内，字数/有限数/控制字符/排序冲突检查复用四阶段规则。

编辑请求带 expected_version 与明确 revision_id。服务核对当前状态和包内容后创建新修订，冲突返回 409，UI 提示刷新，不静默覆盖。第五阶段统一为：流程无活动 Worker 时才允许修改；运行期间修改返回冲突，先取消并等待租约退出或结束，再启动新流程。撤销审批必须立即让未领取下游等待；已有运行中的相关任务标记失效、停止推进，并在提交入口拒绝旧产物。

场景/rank 改动使场景确认和下游草稿/批准失效，重新从 sort/narrate 开始；草稿修改使其批准及 tts/subtitle/mix/export 失效，重新审查后从 tts 开始。重试仅重建失败阶段与需要重建的下游任务，输入沿用明确成功修订；不要无条件重新调用模型。取消保留任务与产物历史；Worker 在进度/心跳/提交处获知取消，无法及时停止的外部进程也不能把迟到结果登记成功。

## 6. REST / SSE 契约（拟新增）

响应沿用现有 JSON 错误规范；409 为版本/流程冲突，400 为非法编辑，403 为治理或文件访问拒绝。新接口都走 loopback/same-origin gate。

| 方法与路径 | 用途及请求关键字段 |
|---|---|
| POST `/api/assets/{id}/workflows` | 启动；revision_id、idempotency_key；响应 run 快照 |
| GET `/api/assets/{id}/workflows` | 分页流程历史 |
| GET `/api/workflows/{run}` | 阶段、任务、输入/输出修订、等待原因及 version |
| POST `/api/workflows/{run}/cancel` | expected_version、reason |
| POST `/api/workflows/{run}/retry` | expected_version、failed_stage、idempotency_key |
| GET `/api/workflows/{run}/review` | 当前可审查场景/草稿、证据文件 key、批准状态；不传绝对路径 |
| POST `/api/workflows/{run}/revisions` | expected_version、base_revision_id、场景或草稿有限字段修改 |
| POST `/api/workflows/{run}/scene-reviews` | expected_version、revision_id、scene_id、decision、note |
| POST `/api/workflows/{run}/narration-reviews` | expected_version、revision_id、narration_id；服务从保存草稿取值 |
| DELETE `/api/workflows/{run}/narration-reviews/{narration}` | 明确版本条件下撤销，触发下游失效规则 |
| GET/POST `/api/workflows/{run}/acceptance` | 获取/追加人工检查记录；提交包版本必须匹配 |

上述流程批准调用统一 service 审查逻辑；旧四阶段批准入口对流程资产也必须核对当前实际草稿，不能绕过修订绑定。既有资产流程外的兼容策略须写入报告，不删除旧接口。

幂等键作用域为操作、asset/run、请求内容；相同键与内容返回原结果，不同内容返回冲突。分页和响应大小设上限。SSE 增加 workflow.changed/review.changed/acceptance.changed，携带 ID/version；客户端重连拉 REST 快照，事件缺失或乱序不决定业务状态。

审计至少记录 workflow.start/cancel/retry、revision.create、scene.review、narration.approve/revoke、workflow.ready、acceptance.record、stale_delivery.reject；记录 actor、对象、版本和原因。脱敏配置摘要不得包含 token、完整模型请求或媒体正文。

## 7. WebUI 框架与交互任务

沿用现有资产选择、交付面板、任务与审计面板。新增流程面板展示七阶段进度、复核停点、等待原因、失败重试和历史包；场景卡片通过既有受控文件端点显示证据图，展示源时刻与来源。草稿审查提供编辑、保存新版本、批准/撤销及审核状态，不用 needs_review=false 表示人已批准。

浏览器不保存模型 token；展示缺配置项与脱敏模型名即可。无图、校验失败、空草稿、审批冲突、网络中断、锁定资产都要有明确状态。批准按钮仅作用于屏幕当前版本，提交前后重新校对 version。键盘可操作、加载时防重复提交、重连不重复启动；窄窗按钮换行且不溢出卡片。具体视觉实现需继承现有样式，避免重做全站布局。

验收面板初始全为“待人工验收”，只有人提交明确结果才记录通过；工程报告与人工结论分开显示。提供最终 ZIP、证据索引、导入说明与可下载的去敏验收摘要，不把内部路径/哈希配置字段堆进普通操作表单。
